  **Subject: Refactor: Consolidate All File Attachments into a Single Pending Message**

  The issue is not fixed. We've tested and  identified an important workflow issue concerning file attachments within
  the main chat interface that needs immediate attention before proceeding with further multimodal integrations.

  **1. The Problem: Multiple Pending Messages for Attachments**

  Currently, when a user attaches files in multiple operations (e.g., first an image, then an audio file, or several
  batches of files), each attachment operation results in a *separate* "pending" message appearing in the chat window.
  This creates visual clutter and a fragmented user experience.

  *   **Observation**: While uploading multiple files *at once* correctly groups them into a single pending message,
  subsequent upload operations (`filesSelected` events) create entirely *new* pending messages.
  *   **Root Cause Analysis (My Understanding)**: The `processFilesFx` effect (in
  [`src/features/chat/model.ts`](src/features/chat/model.ts:199)) always generates a new unique message ID
  (`crypto.randomUUID()`) for each batch of files processed. The subsequent handling then simply appends this newly
  generated message to the main `$messages` store. There is no mechanism in place to identify an *existing, active*
  pending attachment message and append new files to it. The current bundling logic only occurs when the message is
  explicitly sent, but not during the "pending" state management.

  **2. Desired Behavior: A Single, Unified Pending Message**

  My clear requirement is that regardless of how many separate file attachment operations a user performs, all attached
  files (images, audio, documents, recordings) **must coalesce into a single, unified pending message.** This single
  message should persist until the user explicitly sends it (either by typing text and clicking send, or sending the
  media-only message).

  *   There should be **only one (and only one) pending user message** at any given time for attachments.
  *   New attachments should *always* update this single active pending message, not create new ones.

  **3. Proposed Refactoring Plan: Single Source of Truth for Pending Multimodal Messages**

  To address this, we need to refactor the logic responsible for handling file attachments and their representation in
  the chat `$messages` store. The goal is to introduce a single source of truth for the active pending multimodal
  message.

  **3.1. Introduce a Dedicated Store:**
  *   Create a new Effector store: `$activePendingMultimodalMessage = chatDomain.store<Message | null>(null)`. This
  store will hold the *single* `Message` object that represents all current pending attachments and optionally the
  user's draft text.

  **3.2. Refactor `processFilesFx.doneData` Handling:**
  *   Modify the handler for `processFilesFx.doneData` (the event that emits the processed file message) to *not*
  directly append a new message to `$messages`.
  *   Instead, this handler should:
      1.  Check the current state of `$activePendingMultimodalMessage`.
      2.  If `$activePendingMultimodalMessage` is `null` (or invalid for merging), the `Message` returned by
  `processFilesFx` becomes the new `$activePendingMultimodalMessage`.
      3.  If a valid `$activePendingMultimodalMessage` already exists, the content (files/attachments) from the
  `Message` returned by `processFilesFx` should be *merged into* the existing `$activePendingMultimodalMessage` object.
  The `id` of the existing pending message must be preserved.
      4.  Update the `timestamp` of the `$activePendingMultimodalMessage` to reflect the latest modification.

  **3.3. Update `$messages` Store from `$activePendingMultimodalMessage`:**
  *   The main `$messages` store should then be updated to accurately reflect the state of
  `$activePendingMultimodalMessage`. This means:
      1.  If `$activePendingMultimodalMessage` becomes non-null, ensure it's present in `$messages`. If an older version
   exists, replace it.
      2.  If `$activePendingMultimodalMessage` becomes `null`, ensure it's removed from `$messages`.
      3.  Crucially, ensure no other "pending" attachment messages remain in `$messages` if they were somehow created
  incorrectly (though the new flow should prevent this).

  **3.4. Refine `messageSent` Logic:**
  *   The `messageSent` sample (lines 763-886 in [`src/features/chat/model.ts`](src/features/chat/model.ts:763)) which
  currently tries to `find consecutive pending media messages at the end` and bundle them, will need to be simplified.
  *   It should directly take `$activePendingMultimodalMessage` as its source (if it's not null) and combine its content
   with the `$messageText` to form the final `userMessageCreated` payload.
  *   After `userMessageCreated` fires (signaling the message has been sent), `$activePendingMultimodalMessage` must be
  reset to `null`.

  **3.5. Consider Edge Cases:**
  *   Ensure that if the user *only* attaches files (without typing text), and then explicitly clicks a "Send" button
  (if one exists for media-only messages), this still correctly finalizes and sends the
  `$activePendingMultimodalMessage`.
  *   Address any potential race conditions during rapid file attachments.

  **4. Deliverables:**

  Please provide a detailed architectural plan covering the necessary Effector events, stores, and effects, and how they
   will interact to achieve this single-pending-message behavior. Include any necessary Mermaid diagrams to illustrate
  the revised data flow.
