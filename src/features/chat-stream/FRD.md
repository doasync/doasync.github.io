# Feature Requirements Document: Unified Chat Streaming (chat-stream)

**Version:** 2.0
**Date:** 2025-06-08
**Author:** Roo (AI Assistant)

## 1. Introduction

This document details the `chat-stream` feature, a core, stateless, and reusable module designed to provide robust Server-Sent Events (SSE) streaming capabilities from the OpenRouter API. Utilizing Effector for orchestrating the streaming lifecycle and managing internal `AbortController` instances, and `eventsource-parser` for reliable stream parsing, `chat-stream` serves as the foundational streaming mechanism for various application components, including the main chat interface (`src/features/chat/`) and the Mini Chat dialog (`src/features/mini-chat/`).

## 2. Goals

- **Unified Streaming Logic:** Provide a single, consistent mechanism for initiating and managing OpenRouter streaming requests across different application features.
- **Robust SSE Handling:** Reliably parse SSE streams, handling data chunks, completion signals (`[DONE]`), comments, and potential edge cases using `eventsource-parser`.
- **Effective Cancellation:** Implement reliable stream abortion using `AbortController`, triggered via an Effector event, allowing users to stop generation on demand. Cancellation should be silent from the user's perspective (no explicit cancellation message generated by this module).
- **DRY Principle:** Consolidate streaming logic into a dedicated feature module (`src/features/chat-stream/`) to avoid duplication.
- **Reusability & Maintainability:** Design a clean, well-documented API that is easy for other features to consume and straightforward to maintain.
- **Stateless Core:** The `chat-stream` module's core logic remains stateless regarding chat content. Consumers are responsible for generating unique `streamId`s for each request, managing their own message state (including placeholders and `targetMessageId`s), and updating their UI based on the callbacks provided by this feature. `chat-stream` itself focuses on orchestrating the streaming process and internally managing `AbortController` instances associated with active streams.

## 3. Non-Goals

- **UI Implementation:** This feature does not include any UI components. UI elements (like "Stop" buttons or message display) are the responsibility of consuming features.
- **Chat State Management:** This feature does not manage the state of chat conversations (e.g., storing message history). It provides data chunks via callbacks to consumers, who manage their own state.
- **Specific Chat Feature Logic:** Business logic specific to the main chat or MiniChat (e.g., message formatting, retry logic beyond simple cancellation, placeholder message creation) is outside the scope of this feature.

## 4. Functional Requirements

| ID    | Requirement                                | Details                                                                                                                                                                                                                                   |
| :---- | :----------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-01 | Initiate Streaming Request                 | Provide an Effector effect (`streamChatFx`) to start an OpenRouter chat completion request with `stream: true`.                                                                                                                           |
| FR-02 | Accept Parameters                          | `streamChatFx` must accept parameters including OpenRouter details (model, messages, temperature, etc.), API key, **and a consumer-generated `streamId`**, along with callback functions (`onChunk`, `onComplete`, `onError`, `onAbort`). |
| FR-03 | SSE Parsing                                | Utilize `eventsource-parser` to parse the incoming SSE stream.                                                                                                                                                                            |
| FR-04 | Handle Data Events                         | Correctly identify and parse `data: {...}` events, extracting the content delta.                                                                                                                                                          |
| FR-05 | Handle Completion Event                    | Recognize the `data: [DONE]` signal to indicate the end of the stream.                                                                                                                                                                    |
| FR-06 | Handle Comments                            | Ignore SSE comments (lines starting with `:`) like `: OPENROUTER PROCESSING`.                                                                                                                                                             |
| FR-07 | Provide Chunk Callback (`onChunk`)         | Invoke a callback function (`onChunk`) for each valid data chunk received, passing the parsed chunk data and the **received `streamId`**.                                                                                                 |
| FR-08 | Provide Completion Callback (`onComplete`) | Invoke a callback function (`onComplete`) when the stream finishes successfully (either via `[DONE]` or natural stream end), passing the **received `streamId`**.                                                                         |
| FR-09 | Provide Error Callback (`onError`)         | Invoke a callback function (`onError`) when an error occurs during streaming or parsing, passing the error object and the **received `streamId`**.                                                                                        |
| FR-10 | Provide Abort Callback (`onAbort`)         | Invoke a callback function (`onAbort`) when the stream is successfully aborted via `abortStream`, passing the **received `streamId`**.                                                                                                    |
| FR-11 | Stream Cancellation Event                  | Provide an Effector event (`abortStream`) that accepts a payload `{ streamId: string }` to trigger the cancellation of a specific ongoing stream.                                                                                         |
| FR-12 | Reliable Cancellation Implementation       | Use `AbortController` and its `signal` passed to `fetch` to reliably abort the underlying HTTP request and stream processing. `AbortController` instances are managed internally by `chat-stream` using the provided `streamId`.          |
| FR-13 | Silent Cancellation UX                     | Ensure that aborting a stream does not inherently cause a user-visible cancellation message; UI state changes are the consumer's responsibility.                                                                                          |
| FR-14 | Error Reporting                            | Report unrecoverable errors (e.g., initial fetch failure, critical parsing errors) primarily through the rejection of the `streamChatFx` promise. In-stream errors (e.g., chunk parsing errors) are reported via the `onError` callback.  |
| FR-15 | Stream Identification                      | The consumer must assign and provide a unique `streamId` to each streaming request initiated via `streamChatFx`. This ID is used by `chat-stream` for internal `AbortController` management and is passed to all callbacks.               |

## 5. Non-Functional Requirements

| ID     | Requirement     | Details                                                                                                                                                                                                                          |
| :----- | :-------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-01 | Reliability     | Handle common SSE patterns, potential malformed data, and network interruptions gracefully.                                                                                                                                      |
| NFR-02 | Maintainability | Code must be well-structured within `src/features/chat-stream/`, documented, and adhere to project linting and formatting standards.                                                                                             |
| NFR-03 | Reusability     | The feature's API (`streamChatFx`, `abortStream`, types) must be generic enough for use by different chat implementations without modification to the core feature.                                                              |
| NFR-04 | Statelessness   | The core logic (`api.ts`, `model.ts`) must not store chat message content or other feature-specific state. State management is delegated to consumers via callbacks. `chat-stream` only manages the state of `AbortController`s. |
| NFR-05 | Performance     | Stream processing should be efficient and avoid unnecessary blocking or memory consumption.                                                                                                                                      |
| NFR-06 | Testability     | The core logic, particularly in `api.ts`, should be structured to facilitate unit testing.                                                                                                                                       |

## 6. API Design

- **Effect:** `streamChatFx: Effect<StreamChatParams, void, Error>`
- **Event:** `abortStream: Event<{ streamId: string }>`
- **Types:**

  - `StreamChatParams`:

    ```typescript
    // From: src/features/chat-stream/types.ts
    export interface StreamChatParams {
      // Consumer-generated ID for this specific stream request
      streamId: string;

      // Required OpenRouter Params
      model: string;
      messages: Array<{
        role: "system" | "user" | "assistant";
        content: string;
        // name?: string; // Optional name property
        // tool_calls?: Array<any>; // If supporting tool calls
        // tool_call_id?: string; // If supporting tool calls
      }>;
      apiKey: string;

      // Optional OpenRouter Params
      temperature?: number;
      max_tokens?: number;
      top_p?: number;
      // ... other valid OpenRouter params like frequency_penalty, presence_penalty, etc.

      // Callbacks
      onChunk: (payload: StreamChunkPayload) => void;
      onComplete: (payload: StreamCompletePayload) => void;
      onError: (payload: StreamErrorPayload) => void;
      onAbort: (payload: StreamAbortPayload) => void;
    }
    ```

  - `ParsedStreamChunk` (as part of `StreamChunkPayload`):

    ```typescript
    // From: src/features/chat-stream/types.ts
    // Represents the structure of a successfully parsed data chunk from OpenRouter
    export interface OpenRouterParsedChunkData {
      id?: string; // Stream ID from OpenRouter, not the consumer's streamId
      model?: string;
      choices: Array<{
        index?: number;
        delta: {
          role?: "user" | "assistant" | "system";
          content?: string | null;
          // tool_calls?: Array<any>; // If supporting tool calls
        };
        finish_reason?: string | null;
      }>;
      // usage?: { ... }; // Optional usage info
    }

    export interface StreamChunkPayload {
      streamId: string; // Consumer-generated streamId
      chunk: OpenRouterParsedChunkData;
    }
    ```

  - Other callback payloads (`StreamCompletePayload`, `StreamErrorPayload`, `StreamAbortPayload`) simply contain the `streamId`.

- **Error Handling:**
  - Initial fetch errors or unrecoverable issues (e.g., non-200 initial response from OpenRouter) cause the `streamChatFx` promise to reject.
  - Errors occurring during active streaming (e.g., malformed JSON chunk) invoke the `onError` callback.

## 8. Additional Details

### 8.1. Internal Architecture

The `chat-stream` feature is structured as follows:

- **`src/features/chat-stream/index.ts`**: Serves as the public interface, exporting the main `streamChatFx` effect, the `abortStream` event, and all relevant TypeScript types.
- **`src/features/chat-stream/model.ts`**: Contains the core Effector logic.
  - Defines the `streamChatFx` effect. Its handler manages the lifecycle of a stream:
    - It receives `StreamChatParams` (which includes the consumer-generated `streamId`).
    - Creates a new `AbortController` for the request.
    - Stores this `AbortController` in an internal `Map<string, AbortController>` keyed by the `streamId`.
    - Calls `fetchChatStream` from `api.ts`, passing the parameters and the `AbortSignal`.
    - Ensures the `AbortController` is removed from the map in a `finally` block.
  - Defines the `abortStream` event. A watcher for this event looks up the `AbortController` by `streamId` in the map and calls its `abort()` method.
- **`src/features/chat-stream/api.ts`**: Implements the `fetchChatStream` asynchronous function.
  - Constructs and executes the `fetch` request to the OpenRouter API (`/chat/completions` with `stream: true`).
  - Uses the provided `AbortSignal`.
  - Handles initial non-OK HTTP responses by throwing an error (which rejects `streamChatFx`).
  - If the response is OK, it reads the `ReadableStream` body.
  - Uses `eventsource-parser` to parse the SSE stream.
  - For each parsed event:
    - If it's a data chunk, it calls the `onChunk` callback.
    - If it's a `[DONE]` signal, it calls the `onComplete` callback.
    - If an error occurs during parsing or streaming, it calls the `onError` callback.
    - If the stream is aborted via the `AbortSignal`, it catches the `AbortError` and calls the `onAbort` callback.
- **`src/features/chat-stream/types.ts`**: Defines all TypeScript interfaces and types specific to the `chat-stream` feature, such as `StreamChatParams`, callback payloads, and parsed chunk structures.

### 8.2. Integration and Usage Patterns

The `chat-stream` feature is primarily consumed by `src/features/chat/model.ts` (for the main chat interface) and `src/features/mini-chat/model.ts` (for the Mini Chat dialog).

**Consumer Responsibilities:**

Consuming features are responsible for:

1.  **Generating `streamId`:** Before calling `streamChatFx`, the consumer must generate a unique `streamId` (e.g., using `crypto.randomUUID()`). This ID is crucial for associating callbacks and cancellation requests with the correct stream.
2.  **Message State Management:**
    - Managing their own message arrays (e.g., `$messages` in main chat, `$miniChat.messages` in mini-chat).
    - Creating and managing placeholder messages if required by their UI. This involves:
      - Generating a `placeholderId` or `targetMessageId` for the message that will receive the streamed content.
      - Adding a new message object (with `isLoading: true` and empty content) to their state when a stream is initiated, or marking an existing message as loading.
    - Implementing the `onChunk` callback:
      - Identifying the correct message in their state (using `placeholderId` or `targetMessageId`).
      - Appending the received `chunk.choices[0]?.delta?.content` to this message's content.
      - Ensuring the message remains `isLoading: true`.
    - Implementing the `onComplete` callback:
      - Identifying the correct message.
      - Setting its `isLoading` state to `false`.
      - Performing any finalization logic (e.g., triggering saves).
    - Implementing the `onError` callback:
      - Identifying the correct message.
      - Setting its `isLoading` state to `false`.
      - Displaying an error to the user (e.g., by updating the message content).
    - Implementing the `onAbort` callback:
      - Identifying the correct message.
      - Setting its `isLoading` state to `false`.
      - Optionally reverting content or performing other cleanup.
3.  **Loading Indicators:** Managing their own local loading indicators (e.g., `$isGenerating` in main chat, `$miniChat.loading` in mini-chat) based on their specific stream initiation and completion/error/abort events.
4.  **Regeneration/Retry Logic:** If supporting message regeneration or retries, consumers must implement the logic to determine the `targetMessageId` of the message to be updated/replaced and whether a new message (`shouldAddNewMessage`) needs to be created.

### 8.3. Reflection on Resolved Regressions

The design of `chat-stream` and its integration patterns have been instrumental in addressing previous regressions:

- **Message Regeneration Malfunction:** The initial problem (new messages being added instead of replacing existing ones during retry/regeneration) was resolved by shifting the responsibility of identifying the `targetMessageId` and managing message creation/update to the consumer (`src/features/chat/model.ts`). `chat-stream`'s callback mechanism (`onChunk`, `onComplete`, etc.) allows the consumer to direct updates to the correct message, whether it's new or existing. This was detailed in `FIX_PLAN_3.md`.
- **Localized Loading States:** The issue of a global loading state (`streamChatFx.pending`) affecting unrelated UI components was addressed by having consumers manage their own local loading states (e.g., `$isGenerating` in main chat, `$miniChat.loading` in mini-chat). These local states are triggered by consumer-specific events tied to the initiation and finalization (completion, error, or abort) of _their_ streams. `chat-stream` provides the necessary callbacks for consumers to manage these local states effectively, as outlined in `FIX_PLAN_2.md`.
- **Mini Chat Streaming Issues:** Initial problems with Mini Chat's streaming (user message not appearing, placeholder issues, incorrect API history) were fixed by ensuring the consumer (`src/features/mini-chat/model.ts`) correctly sequenced the addition of user messages and placeholders before triggering `streamChatFx`, and by accurately constructing the message history for the API. This was addressed in `FIX_PLAN_1.md`.

These resolutions highlight the robustness of the `chat-stream` feature when consumers correctly implement the integration patterns, particularly around state management and callback handling.

## 9. Future Considerations

- Support for different stream content types (if OpenRouter API evolves).
- More granular callbacks (e.g., `onComment` if detailed comment processing becomes necessary).
- Configurable retry logic for transient network errors within the `chat-stream` module itself (currently, retry logic is handled by consumers).
