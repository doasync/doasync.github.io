# Feature Requirements Document: Unified Chat Streaming (chat-stream)

**Version:** 1.0
**Date:** 2025-04-12
**Author:** Roo (AI Assistant)

## 1. Introduction

This document outlines the requirements for the `chat-stream` feature. The purpose of this feature is to provide a unified, robust, and reusable solution for handling Server-Sent Events (SSE) streams from the OpenRouter API within the application. It leverages Effector for state management orchestration and `eventsource-parser` for reliable SSE parsing. This feature will serve as the foundation for streaming chat completions in various parts of the application, such as the main chat interface and the MiniChat component.

## 2. Goals

- **Unified Streaming Logic:** Provide a single, consistent mechanism for initiating and managing OpenRouter streaming requests across different application features.
- **Robust SSE Handling:** Reliably parse SSE streams, handling data chunks, completion signals (`[DONE]`), comments, and potential edge cases using `eventsource-parser`.
- **Effective Cancellation:** Implement reliable stream abortion using `AbortController`, triggered via an Effector event, allowing users to stop generation on demand. Cancellation should be silent from the user's perspective (no explicit cancellation message generated by this module).
- **DRY Principle:** Consolidate streaming logic into a dedicated feature module (`src/features/chat-stream/`) to avoid duplication.
- **Reusability & Maintainability:** Design a clean, well-documented API that is easy for other features to consume and straightforward to maintain.
- **Stateless Core:** The core streaming logic should remain stateless regarding chat content; consumers manage their own state based on events/callbacks provided by this feature.

## 3. Non-Goals

- **UI Implementation:** This feature does not include any UI components. UI elements (like "Stop" buttons or message display) are the responsibility of consuming features.
- **Chat State Management:** This feature does not manage the state of chat conversations (e.g., storing message history). It provides data chunks via callbacks to consumers, who manage their own state.
- **Specific Chat Feature Logic:** Business logic specific to the main chat or MiniChat (e.g., message formatting, retry logic beyond simple cancellation) is outside the scope of this feature.

## 4. Functional Requirements

| ID    | Requirement                                | Details                                                                                                                                                                    |
| :---- | :----------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-01 | Initiate Streaming Request                 | Provide an Effector effect (`streamChatFx`) to start an OpenRouter chat completion request with `stream: true`.                                                            |
| FR-02 | Accept Parameters                          | `streamChatFx` must accept parameters including OpenRouter details (model, messages, temperature, etc.), API key, and callback functions.                                  |
| FR-03 | SSE Parsing                                | Utilize `eventsource-parser` to parse the incoming SSE stream.                                                                                                             |
| FR-04 | Handle Data Events                         | Correctly identify and parse `data: {...}` events, extracting the content delta.                                                                                           |
| FR-05 | Handle Completion Event                    | Recognize the `data: [DONE]` signal to indicate the end of the stream.                                                                                                     |
| FR-06 | Handle Comments                            | Ignore SSE comments (lines starting with `:`) like `: OPENROUTER PROCESSING`.                                                                                              |
| FR-07 | Provide Chunk Callback (`onChunk`)         | Invoke a callback function (`onChunk`) for each valid data chunk received, passing the parsed chunk data and a unique `streamId`.                                          |
| FR-08 | Provide Completion Callback (`onComplete`) | Invoke a callback function (`onComplete`) when the stream finishes successfully (either via `[DONE]` or natural stream end), passing the `streamId`.                       |
| FR-09 | Provide Error Callback (`onError`)         | Invoke a callback function (`onError`) when an error occurs during streaming or parsing, passing the error object and the `streamId`.                                      |
| FR-10 | Provide Abort Callback (`onAbort`)         | Invoke a callback function (`onAbort`) when the stream is successfully aborted via `abortStream`, passing the `streamId`.                                                  |
| FR-11 | Stream Cancellation Event                  | Provide an Effector event (`abortStream`) that accepts a payload `{ streamId: string }` to trigger the cancellation of a specific ongoing stream.                          |
| FR-12 | Reliable Cancellation Implementation       | Use `AbortController` and its `signal` passed to `fetch` to reliably abort the underlying HTTP request and stream processing.                                              |
| FR-13 | Silent Cancellation UX                     | Ensure that aborting a stream does not inherently cause a user-visible cancellation message; UI state changes are the consumer's responsibility.                           |
| FR-14 | Error Reporting                            | Report unrecoverable errors (e.g., initial fetch failure, critical parsing errors) primarily through the rejection of the `streamChatFx` promise. May also use `onError`.  |
| FR-15 | Stream Identification                      | Assign a unique `streamId` to each streaming request initiated by `streamChatFx`. This ID must be passed to all callbacks (`onChunk`, `onComplete`, `onError`, `onAbort`). |

## 5. Non-Functional Requirements

| ID     | Requirement     | Details                                                                                                                                                              |
| :----- | :-------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-01 | Reliability     | Handle common SSE patterns, potential malformed data, and network interruptions gracefully.                                                                          |
| NFR-02 | Maintainability | Code must be well-structured within `src/features/chat-stream/`, documented, and adhere to project linting and formatting standards.                                 |
| NFR-03 | Reusability     | The feature's API (`streamChatFx`, `abortStream`, types) must be generic enough for use by different chat implementations without modification to the core feature.  |
| NFR-04 | Statelessness   | The core logic (`api.ts`, `model.ts`) must not store chat message content or other feature-specific state. State management is delegated to consumers via callbacks. |
| NFR-05 | Performance     | Stream processing should be efficient and avoid unnecessary blocking or memory consumption.                                                                          |
| NFR-06 | Testability     | The core logic, particularly in `api.ts`, should be structured to facilitate unit testing where possible (e.g., dependency injection for `fetch` if needed).         |

## 6. API Design (Preliminary)

- **Effect:** `streamChatFx: Effect<StreamChatParams, void, Error>`
- **Event:** `abortStream: Event<{ streamId: string }>`
- **Types:**

  - `StreamChatParams`:

    ```typescript
    interface StreamChatParams {
      // Required OpenRouter Params
      model: string;
      messages: Array<{
        role: "system" | "user" | "assistant";
        content: string;
      }>;
      apiKey: string;

      // Optional OpenRouter Params
      temperature?: number;
      // ... other valid OpenRouter params

      // Callbacks
      onChunk: (payload: {
        streamId: string;
        chunk: ParsedStreamChunk;
      }) => void;
      onComplete: (payload: { streamId: string }) => void;
      onError: (payload: { streamId: string; error: Error }) => void;
      onAbort: (payload: { streamId: string }) => void; // Called on successful abort action
      // Optional: onStart: (payload: { streamId: string }) => void;
    }
    ```

  - `ParsedStreamChunk`: Interface representing the structured data extracted from a `data:` event (e.g., `{ choices: [{ delta: { content: string } }] }`).

- **Error Handling:**
  - Initial fetch errors or unrecoverable issues reject the `streamChatFx` promise.
  - Errors during active streaming invoke the `onError` callback.

## 7. Dependencies

- `effector` (and related ecosystem packages like `patronum` if used)
- `eventsource-parser`

## 8. Future Considerations

- Support for different stream content types (if OpenRouter API evolves).
- More granular callbacks (e.g., `onComment`, `onStart`).
- Configurable retry logic for transient network errors (currently outside scope).
